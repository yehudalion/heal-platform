## 1. איך לעבוד עם ליאון

- **עברית בלבד.** קוד, SQL ושמות קבצים באנגלית. הכול השאר עברית.
- **תמציתי וישיר.** בלי הקדמות, בלי "אני אעשה עכשיו...", בלי סיכומים ארוכים
  של מה שכבר ראה. הוא עוקב תוך כדי.
- **הוא סומך על עבודה אוטונומית ארוכה.** כשהוא אומר "תעשה את כל המנות עכשיו"
  הוא מתכוון לזה — לא לעצור בין שלבים לאישור. אבל **הוא כן רוצה לדעת על
  הכרעות שקיבלת בדרך**, במיוחד כשסטית מהפרוטוקול.
- **כשיש החלטת מוצר אמיתית — לשאול, לא לנחש.** הוא הכריע דברים כמו "בחירה =
  חיכוך" ו"אין ענישה" בעצמו, ואלה החלטות שמגדירות את המוצר.
- **הוא לא מפתח מקצועי.** כשצריך שיריץ משהו — לתת פקודה מדויקת להעתקה,
  לא הסבר כללי. אם צריך לערוך קובץ — לערוך בעצמך, לא להסביר לו מה לשנות.
- **אל תסמוך על דיווח קודם שלך על "הצלחה" ב-DB.** קרה בפועל: דווח שמנה ח'
  נכתבה, ושאילתה גילתה 0 שורות. **תמיד לאמת בשאילתה.**

## 4. פרוטוקול ייצור מנה — הידע היקר ביותר במסמך הזה

זה התהליך שהתגבש על פני 9 מנות. **מי שיפעיל אותו שוב (למשל למודול אחר)
צריך לעקוב אחריו בדיוק** — כל שלב נוסף בגלל כישלון אמיתי.

### השלבים
1. **כתיבה** — 3 סוכנים מקבילים (קצר/בינוני/ארוך לפי דלי), עם **הפרדת
   תחומי-נושא מפורשת** לכל סוכן + **רשימת החרגה מצטברת** של כל נושא
   שנעשה בו שימוש בכל מנה קודמת.
2. **אימות מבני משלי** (`verify_batch.py` ב-outputs) — Python, לא סוכן.
3. **שער דליפה מכני** — `python3 scripts/qa_lecture_qa_leakage.py <gate_input.json> --strict`
4. **תיקון** האזהרות/חסימות.
5. **שני פותרים עיוורים** במקביל: אחד **עם** תמליל (בדיקת פתירוּת), אחד
   **בלי** תמליל (בדיקת דליפה).
6. **ניקוד מול הבסיס** (ראו כלל הפרשנות למטה).
7. **כתיבה ל-DB** → **אימות ספירה בשאילתה** → **ארכוב JSON** ל-`docs/archive/`
   → **עדכון SITEMAP**.

### כלל פרשנות הדליפה — קריטי, לא אינטואיטיבי
בסיס הבחינה האמיתית: **~92%**.

- **דליפה גבוהה מהבסיס (95%+, ובמיוחד 100%)** = 🔴 **כשל תקפות.** התלמיד
  יכול לנחש בלי לשמוע. **חייב סבב תיקון.**
- **דליפה נמוכה מהבסיס** (מנה ז' יצאה 83.3%) = ✅ **לא פגם.** משמעו שהמסיחים
  קשים יותר לפסילה בהיגיון טהור. ניטרלי-עד-חיובי לתקפות.

**אל תתקן דליפה נמוכה.** זו טעות שקל ליפול בה.

### מה גורם לדליפה — הדפוסים שנמצאו בפועל
כשהפותר-בלי-תמליל מנחש נכון, זה כמעט תמיד אחד מאלה:
- **חוסר-התאמה דקדוקי בין אופציות** — למשל שם פרטי יחיד ("Tom") באופציה
  אחת כשהשאלה על נושא רבים ("המתנדבים").
- **ניגוד תמאטי-מילוני** — מילה שמתנגשת עם הטון של הקטע ("אוטומטי" מול "מסורת").
- **היפוך עצמי-סותר** — מסיח שחוזר על הנחת השאלה בכיוון הפוך, ולכן פסול מיידית.
- **טעם זמני מפורש** — "אחרי שהחריטה הסתיימה" בשאלת "מה השלב הראשון".
- **צביר-ערכיוּת** — 3 מסיחים שליליים + תשובה חיובית אחת (בסיפורי תיקון
  התוצאה תמיד חיובית).
- **מילות מוחלטוּת** — "always" / "every" במסיחים בלבד.

**מה כן לגיטימי להשאיר:** היגיון-רצף גנרי ("מה השלב הראשון" — מנקים לפני
שמדביקים) וידע אוצר-מילים אמיתי בשאלות `vocab_in_context`. אלה חלק מארכיטיפ
סוג-השאלה ולא ניתן להסירם בלי לשנות את הפורמט.

### מפרט מבני (נאכף ב-`verify_batch.py`)
- **מילים:** s30: 65–135 · s60: 142–176 · s90: 215–310
- **שאלות:** s30: 1 · s60: 2 · s90: 2
- **`difficulty`:** s30→2 · s60→3 · s90→4
- **`wpm_target`:** dialogue→170 · lecture→155
- **`question_type`:** `main_idea` · `detail` · `speaker_ref` · `negative` ·
  `opinion` · `vocab_in_context` (`continuation` הוא ערך שביעי לסוג פריט אחר).
  **"why" אינו ערך תקף** — ממופה ל-`detail`.
- **`target_zone`:** `early` / `late` בלבד (NULL מותר). **"mid" אינו תקף —
  יש CHECK constraint קשיח ב-DB.**
- דיאלוג: בדיוק 2 דוברים בשמות, שורות בפורמט `Name: text`
- **אין ספרות בשום מקום** בתמליל או באופציות
- `highlight_spans` חייבים להיות **תת-מחרוזת מילולית מדויקת** מהתמליל
- s90-lecture: בדיוק 2 נקודות ציר (`However` / `Yet`)
- **איות אמריקאי בלבד** (רשימת חסימה מפורשת: colour, favour, organise,
  centre, theatre, defence, licence, practise, grey, tyre, ...)
- בדיוק 4 אופציות; `correct_option_index` תואם את מיקום ה-`k_code=='CORRECT'`
- **פיזור אורך אופציות ≤ 3 מילים**
- שאלת `main_idea` חייבת לפחות מסיח אחד עם `fail_mode=='rival_claim'`

## 5. באגים שעלו זמן — לא ליפול בהם שוב

### 5.1 `anchor_back_sentences` — שגיאת syntax ב-DB
העמודה `listening_questions.anchor_back_sentences` היא **`integer`**, אבל
סוכני כתיבה מילאו אותה במערכים של משפטי-ציטוט. `str(list)` בפייתון ייצר
SQL לא תקין → `ERROR: 42601: syntax error at or near "["`.

**מניעה:** לקבע `NULL` תמיד ביצירת ה-SQL, ולהגיד לסוכני הכתיבה במפורש
לא למלא את השדה.

### 5.2 UUID מחדש — כפילות/יתמות שקטה
פונקציית `build_sql()` מייצרת `uuid.uuid4()` חדש **בכל קריאה**. אם קוראים
לה פעמיים על אותה מנה (למשל כדי לתקן באג), ה-lecture_id החדשים **לא
יתאימו** לשורות שכבר נכתבו.

**מניעה:** לפני הרצת SQL שנוצר מחדש — **לשאול את ה-DB** אם השורות כבר שם:
```sql
select id, title from listening_lectures where generation_batch='LQA-PROD-X' order by title;
```
אם כן — לגזור את ה-id לפי התאמת כותרת, ולכתוב מחדש **רק את השאלות**.

### 5.3 באג הקצאת קולות — חזר פעמיים
ב-`scripts/generate-lecture-qa-audio.js`, המפה `KNOWN_GENDER` מקצה מגדר
לשמות דוברים. **אם שני דוברים באותו דיאלוג ממופים לאותו מגדר — שניהם
מקבלים אותו קול.**

- פעם ראשונה (מנה ב'): באג בקורסור — 3 דיאלוגים יצאו בקול זהה. תוקן 16.8.
- פעם שנייה (מנה ט', 17.8): `noor` ו-`callum` היו **שניהם `'m'`**. תוקן —
  `noor` הועבר ל-`'f'`.

**מניעה:** כשמוסיפים שמות חדשים ל-`KNOWN_GENDER`, לוודא שכל זוג דוברים
שמופיע יחד בדיאלוג מקבל מגדרים שונים. יש שומר-קשיח שזורק שגיאה, אז זה
נתפס — אבל רק בזמן רינדור.

### 5.4 כיול משך אודיו — מתי צריך `--start-rate`
הרינדור מכייל אוטומטית עד `MAX_PASSES = 5`. לפעמים קטע לא מתכנס ונשאר
מחוץ למעטפת. ברוב המקרים **`--force` פשוט מספיק** (הרינדור לא דטרמיניסטי) —
3 מתוך 4 התכנסו כך. לקטע עקשן:
```
node scripts/generate-lecture-qa-audio.js --id <uuid> --force --start-rate 1.12
```
(`--start-rate` נכבד **רק** בהרצת `--id` יחידה.)

## 6. פקודות שליאון מריץ אצלו

הסביבה שלי (הסוכן) **אין לה גישה ל-Google TTS ולא ל-ffmpeg** — כל רינדור
אודיו רץ אצל ליאון. הוא מדביק את הפלט חזרה לצ'ט לאבחון.

```bash
# רינדור כל מה שחסר (מזהה אוטומטית audio_url IS NULL — בטוח מול קיים)
node scripts/generate-lecture-qa-audio.js --all

# קטע יחיד מחדש
node scripts/generate-lecture-qa-audio.js --id <uuid> --force

# קטע עקשן שלא מתכנס למעטפת המשך
node scripts/generate-lecture-qa-audio.js --id <uuid> --force --start-rate 1.12

# שער QA אודיו
python3 scripts/qa_listening_audio.py scripts/audio_output_lecture_qa --type lecture_qa --strict

# שער דליפה תוכן
python3 scripts/qa_lecture_qa_leakage.py <gate_input.json> --strict
```

**דרוש ב-`env.scripts.txt`:** `GOOGLE_TTS_API_KEY`, `SUPABASE_URL`,
`SUPABASE_SERVICE_KEY`. דרוש ב-PATH: `ffmpeg`, `ffprobe`.

## 8. ארבע ההחלטות הפתוחות — ממתינות לליאון

**זה בדיוק המקום שבו השיחה נעצרה.** אלה נשאלו ולא נענו:

### שאלה 1 — מה המטרה של סבב ה-UI/UX?
ארבעה מסלולים, כל אחד מוביל לתוכנית אחרת:
- **(א) לבנות את השדרה החסרה** — אונבורדינג → מנה יומית → המשכיות.
  זה מה שמחבר את 250 הקטעים לתלמיד אמיתי.
- **(ב) לפרסם את תוכן ההאזנה** — בקרת איכות → `is_published=true` → נגישות.
  המודול כבר בנוי; רק לחבר תוכן.
- **(ג) אחידות ומערכת עיצוב** — לאחד שלוש מערכות, לבנות שכבת קומפוננטות.
- **(ד) מובייל תחילה** — לתקן ניווט שבור ולעבור לתכנון מובייל-פירסט.

### שאלה 2 — טלפון או מחשב?
על איזה מכשיר תלמיד היל"ל אמיתי ילמד ברוב הזמן? **זו ההחלטה שמשפיעה על
כל השאר.** אם טלפון — הסיידבר הופך לניווט תחתון וכל מסך נבנה ל-375px קודם.

### שאלה 3 — לוח הבקרה: כפתור אחד או שלוש נקודות כניסה?
**יש כאן סתירה בין שתי החלטות של ליאון עצמו:**
- ב-16.8 הכריע שבהאזנה "בחירה = חיכוך" והוריד לכפתור אחד (מתועד ב-SITEMAP §3).
- אבל SITEMAP §1 עדיין מגדיר בבית **שלוש נקודות שוות-מעמד**
  (התחל כאן / המשך / בחר נושא).

איזה עיקרון גובר? אפשרויות: כפתור אחד ראשי + "בחר נושא" כקישור שקט ·
שלוש נקודות כמו שכתוב · כפתור ראשי + רשת מודולים מתחתיו.

### שאלה 4 — מה עושים עם ה-🔥 "רצף ימים"?
מופיע ב-`home.js` וב-`layout.js`, סותר ישירות את כלל הרווחה. בהאזנה כבר
הוסר. אפשרויות: להסיר לגמרי · להחליף במונה מצטבר שלא נשבר ("סה"כ ימי
לימוד") · להשאיר ולעדכן את SITEMAP (אם ליאון שינה דעה).
